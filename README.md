# Employee Attendance & Analytics API (FastAPI + PyMongo + MongoDB)

A REST API for employees, attendance (punch-in, punch-out, manual corrections), four analytics reports, and an
admin endpoint that shows MongoDB's own query plans. All application code is in `app/main.py`.
The official contract is `openapi.yaml`.

## Prerequisites
* Python 3.11 or newer
* MongoDB 6.0 or newer (the analytics use `$setWindowFields`, `$dateAdd` and `$dateDiff`, which need 5.0+; 7.0 is the target).
  A local server or an Atlas cluster both work.
* `pip` (and optionally `git`)

## Environment variables
| Name | Required | Meaning |
|---|---|---|
| `MONGO_URI` | yes | MongoDB connection string, e.g. `mongodb://localhost:27017` or a `mongodb+srv://...` Atlas URI |
| `MONGO_DB` | yes | Database name to use |
| `TEST_MONGO_URI` | tests only | MongoDB used by the test suite (default `mongodb://127.0.0.1:27017`) |

There are **no defaults** for `MONGO_URI` / `MONGO_DB`: if one is missing the API answers 503 instead of silently using
localhost. A local `.env` file is read for convenience, but real environment variables always win. Do not commit `.env`.

## Installation
```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export MONGO_URI="mongodb://localhost:27017"
export MONGO_DB="attendance_db"
```

## Seed the database (optional)
```bash
python sample_seed.py
```
This loads the nine sample documents from `sample_data/` using `MONGO_URI` / `MONGO_DB`.
**Warning:** it first deletes every document in the `employees` and `attendance_logs` collections of that database.
The samples only show document shapes. They are far too small to judge query plans: for a ~100,000-record check use
`tests/test_explain_live.py` (see below), which builds its own throw-away dataset.

## Run
```bash
uvicorn app.main:app --port 8000
```
(Uvicorn needs the `module:attribute` form, so the command ends in `app.main:app`, not just `app.main`.)

All indexes are created at startup, idempotently (same names and definitions are a no-op on restart).
`GET /health` returns 200 only when MongoDB answers a ping, otherwise 503.

## Query explain (`GET /admin/explain/{endpoint}`)
`endpoint` is one of `attendance_list`, `employee_monthly`, `department_summary`, `late_leaderboard`, `department_trend`.
The endpoint builds the same query or aggregation pipeline as the real endpoint from the same parameters, asks MongoDB to
`explain` it with `executionStats`, and returns `{"endpoint", "collection", "explain"}` where `explain` is MongoDB's
raw answer (nothing is added, removed or hard-coded). Examples:
```bash
curl "localhost:8000/admin/explain/attendance_list?status=LEAVE&date_from=2026-07-01&date_to=2026-07-31&page=2"
curl "localhost:8000/admin/explain/employee_monthly?emp_code=EMP0001&month=2026-07"
curl "localhost:8000/admin/explain/department_summary?month=2026-07"
curl "localhost:8000/admin/explain/late_leaderboard?month=2026-07&limit=5"
curl "localhost:8000/admin/explain/department_trend?department=Engineering&from=2026-07-01&to=2026-07-31"
```
Unknown endpoint names, missing required parameters (`employee_monthly`: `emp_code`, `month`; `department_summary` and
`late_leaderboard`: `month`; `department_trend`: `department`, `from`, `to`) and invalid values answer 422.

## Tests
```bash
pip install -r requirements-dev.txt
python -m pytest tests -v -rs                         # everything
python -m pytest tests/test_explain.py -q             # explain input/contract tests (no MongoDB needed)
python -m pytest tests/test_explain_live.py -v -rs -s # ~100k records, real explain (needs MongoDB)
```
Tests that need MongoDB use `TEST_MONGO_URI` and throw-away database names (dropped afterwards); they never touch `MONGO_DB`.
When MongoDB is unreachable those tests are reported as **skipped**, never as passed.

## Known limitations
* `GET /admin/explain/...` really executes the query (that is what `executionStats` means) and has no authentication
  (the contract defines none). It should not be exposed publicly.
* Skip/limit pagination gets slower for very deep pages, and `total` is an exact count on every list request.
* Startup builds all indexes before the app serves traffic; on a very large existing collection that takes a while.
  If existing data contains duplicate `(emp_code, date)` rows the unique index cannot be built: `/health` stays 200 and
  writes fail instead of silently allowing duplicates.
* An already-existing index with the same keys but a different name would make index creation fail (not handled).
* Interpretation choices where the contract is open: the 92-day trend limit counts both end dates; the 7-day moving average
  uses the already-rounded daily rates; logs dated before an employee's `joined_on` still count; a punch-out earlier than or
  equal to the employee's only punch-in answers 422.
* A malformed `date` string in seeded data is treated as a weekend day by the analytics instead of failing the request.
